# TiDB Cloud Starter compatibility and setup

This is a source/configuration review, not a live database certification. No TiDB connection, SQL query, schema change, credential reset, data import or resource creation was performed. Only offline tests with mocks were used for this addition. Existing MySQL migrations and business logic are unchanged.

## Findings

| Existing requirement | TiDB review and remaining condition |
| --- | --- |
| Four independent schemas | Keep `mediconnect_auth`, `mediconnect_patient`, `mediconnect_doctor`, `mediconnect_appointment` in one MySQL-compatible Starter instance. Each has its own Flyway history/user. Do not combine tables into `test` or change UUIDs |
| `BINARY(16)` UUIDs; nullable ownership/active-slot unique keys | Supported TiDB types/unique semantics. UUIDs are generated by the existing application, not TiDB sequences. Multiple NULLs must remain allowed; `appointments.active_slot_id` remains the database uniqueness barrier for active bookings |
| `DATETIME(6)`, `DATE`, `DECIMAL(9,2)`, BOOLEAN, BIGINT version | Supported type families; UTC JDBC/session settings are explicit. Existing decimal validation and microsecond timestamps remain unchanged |
| Primary/unique indexes, same-schema foreign keys | Supported on modern TiDB; foreign keys are GA from v8.5. Existing child/parent UUID types match, and none are partitioned. Confirm actual service version, `foreign_key_checks=ON`, and three enforced FKs after migration. There are deliberately no cross-service FK constraints |
| Four CHECK constraints | **Deployment gate:** TiDB disables CHECK support by default. `ck_accounts_role`, `ck_doctor_experience`, `ck_doctor_fee`, and `ck_booking_state` must actually exist and be enforced. Merely accepting CREATE TABLE syntax is insufficient |
| Booking/cancellation transactions and `PESSIMISTIC_WRITE` | TiDB supports pessimistic transactions and `SELECT ... FOR UPDATE`. The profile's callback requires session mode `pessimistic`; it never changes cluster/session modes. Repeat the two-session booking and cancellation concurrency tests on the actual Starter target. Distributed conflicts/timeouts and snapshot behavior cannot be certified by H2/mocks |
| JPA repositories/search/pagination | Standard Hibernate JPQL/criteria and generated SQL; no stored procedures, triggers, full-text indexes, engine-specific native application queries, or unsupported SERIALIZABLE isolation were found. `MySQLDialect` follows PingCAP guidance; no community dialect dependency added |
| Flyway | Installed `flyway-mysql`/core **12.4.0** and Connector/J **9.7.0** were inspected, including packaged JARs. Offline tests confirm the installed MySQL adapter recognizes MySQL metadata containing a TiDB version; this is not a successful real migration. Its advisory migration locks and actual server metadata still need validation. No extra TiDB extension or dependency upgrade was assumed necessary |
| Schema collation | The previous MySQL `utf8mb4_0900_as_cs` instruction is unsuitable for this TiDB target. Use supported `utf8mb4_0900_bin` on fresh schemas and JDBC connections (modern TiDB). It is case/accent sensitive and NO PAD, but binary ordering differs from Unicode linguistic ordering; verify doctor name sorting. Do not alter existing schemas/data to force compatibility |
| Connections | Five pooled connections per service, 20 total before rolling-deploy overlap. TiDB Starter limits connection lifetimes and AWS endpoint idle time; the TiDB profile uses max lifetime 300 seconds and keepalive 120 seconds. These checks/handshakes consume RUs; monitor the free quota |
| TLS | Connector/J remains MySQL protocol with `sslMode=VERIFY_IDENTITY`, TLS 1.2/1.3, and JVM trusted CA roots. No certificate/hostname verification is disabled; no `allowPublicKeyRetrieval` or insecure SSL fallback is added. Standard Starter endpoints use public CA certificates. A custom CA remains optional via the existing PEM-to-truststore entrypoint |

`application-tidb.yml` is added only for the four DB services and applied **after** `render`. Discovery and Gateway retain only `render`. Local profiles are unchanged.

The four `TiDbDeploymentChecks` callbacks execute one SELECT before Flyway validation/migration. They require a TiDB server, CHECK enforcement enabled, foreign-key checks enabled, and pessimistic transactions. Missing variables, insufficient read permissions, or a failed check stop startup with a sanitized error. They perform no SET/DDL/DML and never enable settings, fix data, disable constraints, or retry writes. A startup failure here is a blocker, not permission to bypass the check.

## TiDB console steps — do not execute database operations until approved

Account creation and GitHub linking are complete according to the owner. This agent has no authenticated TiDB API/CLI/dashboard channel. No credentials should be pasted into chat or committed.

1. In **TiDB Cloud -> My TiDB**, inspect your selected instance. Confirm **Starter, MySQL Compatible** (not the PostgreSQL-compatible preview), region, and spending limit. If no instance exists, wait for explicit creation approval. Do not upgrade or enable paid spending; keep the spending limit at zero unless separately approved. Prefer the same region as Render when available; do not recreate an existing database solely to move it.
2. Choose **Connect -> Public**; select the intended database branch (normally `main`) and Java/JDBC/General connection instructions. Record hostname and port locally. Use the supplied full/prefixed SQL user name exactly; GitHub login/email is not a database user. Preserve existing passwords; generate a password only for a deliberately new SQL user through the console. Do not reset an existing root password as a connection shortcut.
3. **After permission for a read-only check**, run [tidb-preflight.sql](tidb-preflight.sql) in the console SQL editor or your existing TLS Workbench connection. Confirm TiDB version, CHECK=ON, FK=ON, transaction mode=pessimistic, supported collation, intended schema and negotiated TLS where the client exposes it. SQL-editor TLS evidence describes that connection, not Render JDBC. No live execution has occurred during preparation.
4. If CHECK=OFF, stop. Only after explicit approval for that configuration change, an authorized database administrator can attempt `SET GLOBAL tidb_enable_check_constraint = ON;` and repeat the read-only check in a new session. This setting is global for the instance. If Starter permissions/capabilities prevent enabling it, **this target is blocked**; contact PingCAP or choose another approved MySQL-compatible plan/provider. Do not remove CHECK clauses or treat an ignored constraint as enforced. Enabling the switch does not reconstruct previously omitted constraints; inspect any already-populated schema before proceeding.
5. **After schema/user creation approval**, use the console SQL editor to create only missing, empty application schemas, for example `CREATE DATABASE mediconnect_auth CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin;`. Repeat for the other three names. Do not run CREATE against a name that already exists, drop/clean/recreate a schema, or apply the collation to existing data without a migration review. Existing V1/V2 migration checksums are preserved.
6. In the instance's SQL user management, create four dedicated application users (or use approved existing dedicated users). Grant only the corresponding schema's SELECT/INSERT/UPDATE/DELETE/CREATE/ALTER/INDEX/REFERENCES privileges needed by the existing app/Flyway. `CREATE USER`/GRANT may require an administrator. Keep the provider's exact generated user prefix. Do not use the console organization role as a substitute for SQL grants, or supply the root user to every service.
7. Where Starter provides public endpoint IP/firewall rules, allow the selected Render region's outbound ranges and a temporary approved administrator address. Exact networking options depend on the selected plan; do not assume a private Render hostname can reach a TiDB private endpoint. This configuration uses verified TLS over the public endpoint. No public allow-all rule is created here.
8. In **Data -> Backup**, confirm the actual backup snapshot and recovery options. Free MySQL Starter currently has daily backups with one-day retention; recovery/export requirements must be agreed before importing valuable data. A restore rehearsal creates a separate destination and needs its own approval. Never import over the existing local or cloud database.
9. Set service credentials only in Render's environment dashboard using the names below. Do not start DB services until CHECK/privilege/collation checks are confirmed and permission to run Flyway migrations is given. Then verify every Flyway history plus SHOW CREATE TABLE, and test known-invalid constraint writes only in an approved disposable test schema. A fresh migration pass and same-slot race test remain pending.

## JDBC values and environment names

For each corresponding `AUTH_DB_URL`, `PATIENT_DB_URL`, `DOCTOR_DB_URL`, `APPOINTMENT_DB_URL`:

```text
jdbc:mysql://TIDB_PUBLIC_HOST:TIDB_PORT/mediconnect_auth?sslMode=VERIFY_IDENTITY&enabledTLSProtocols=TLSv1.2,TLSv1.3&characterEncoding=UTF-8&connectionCollation=utf8mb4_0900_bin&connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true
```

Substitute the selected schema and the exact hostname/port from **Connect**, not a localhost address or a guessed port. Put each user/password in its separate `*_DB_USER`/`*_DB_PASSWORD` variables; never embed either in the URL. Database URL options must agree with the profile; do not override verified TLS with insecure options. The active profiles for those services are `render,tidb`.

Standard Starter TLS requires **no** `MYSQL_CA_CERT`, `MYSQL_TRUSTSTORE_URL` or `MYSQL_TRUSTSTORE_PASSWORD`. Leave those optional variables unset; Connector/J uses the Java runtime CA roots and checks the endpoint hostname. If a provider-approved custom CA is required later, use the existing secret-file workflow; do not download an unverified certificate or bypass verification to fix a handshake.

Required names (no values): `AUTH_DB_URL`, `AUTH_DB_USER`, `AUTH_DB_PASSWORD`, `PATIENT_DB_URL`, `PATIENT_DB_USER`, `PATIENT_DB_PASSWORD`, `DOCTOR_DB_URL`, `DOCTOR_DB_USER`, `DOCTOR_DB_PASSWORD`, `APPOINTMENT_DB_URL`, `APPOINTMENT_DB_USER`, `APPOINTMENT_DB_PASSWORD`. JWT secret files and the other deployment variables remain listed in [.env.example](.env.example).

## Current limitations and costs

The first five eligible MySQL-compatible Starter instances currently include 5 GiB row storage, 5 GiB columnar storage and 50 million RUs/month each. The zero-spending-limit path can reject new connections/throttle existing ones when quotas are exhausted; it is not an unlimited always-on capacity guarantee. Four schemas can share a single instance and its quota; four paid databases are not necessary. The account's actual quota/plan was not inspected directly.

The Render draft still uses six paid `1c-2g` services at approximately $150/month before taxes/usage; no paid resource is approved or created. Netlify's free allowance is separately metered. Removing the earlier Aiven recommendation does not make Render private services free.
